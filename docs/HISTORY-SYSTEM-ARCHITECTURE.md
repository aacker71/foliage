## 1. THE ASCENT

Six levels, settled by owner decision (ENGINEERING-PLAN §1): **canopy › tree (a company) › bough (an organization) › branch (a team) › leaf (one person) › leaflet (one artifact)**. Each paragraph says what the level IS, what it may assert, and — the part that is the design — **what it refuses to compute.**

**LEAFLET.** One artifact of evidence: `{id, title, tier, provenance?, reason?}` (`packages/leaf/src/leaf.ts:60-85`), with `LEAFLET_KEYS` a closed set of exactly those five (`packages/leaf/src/document.ts:68-74`). It may assert one thing about one artifact and must carry the handle by which a reader re-checks it. It refuses to compute *anything*: there is no derived field on a leaflet, and the parse gate refuses score-shaped keys by name — `confidence`, `weight`, `strength` among seventeen (`document.ts:82-100`). The tier is not a grade: `ProofTier` is three values with no comparator and no numeric mapping, in either direction (`leaf.ts:30-48`).

*The count is inflatable, so the count is never the rendered thing.* `apps/leaf/src/gitIntake.ts:66-67` already names the hazard for one case — `--no-merges`, because a merge "records an integration, and counting it as evidence of work would inflate the ledger" — and every count above the leaflet inherits it. Splitting one change into twenty signed commits yields twenty verified leaflets at no cost. Cryptography proves WHO, never HOW MUCH.

*Identity across runs.* Two producers exist and they do not agree. Git intake is content-addressed: `id: leafletId(\`${GIT_SOURCE}:${sha}\`)` (`packages/leaf/src/intake.ts:460`). Photosynthesis promotion is not: `id: \`photosynthesis-${c.id}\`` keyed on a candidate id, with `ref` falling back to the literal string `"unknown"` (`apps/photosynthesis/src/promote.ts:45`, `:50`). The identity rule belongs to the capture spec, which is on disk and has now decided it: candidate ids are content-derived (`drafter.ts:61-67`), element ids are `${candidate.id}-e0`, and the `"unknown"` fallback at `promote.ts:50` is deleted once `Candidate.evidence` is a non-empty tuple (LEAFLET-CAPTURE-SPEC §4, §5 item 9). What that spec deliberately does **not** settle is the `Provenance.ref` divergence itself — git intake writes a bare sha, promote writes `<source>:<ref>` — so the shared-ref join ENGINEERING-PLAN §7:229-232 wants remains impossible, and it is an open owner decision there (§9.1), not a gap here.

**LEAF.** The compound: `{id, subject, leaflets[]}` (`leaf.ts:87-92`) — one person's portfolio, and the person owns it. It may assert the set of its own leaflets and a per-tier tally: `attributionLedger` returns `{verified, pending, excluded, exclusionReasons}` and states the refusal in place — "never a ratio, percentage, or composite" (`leaf.ts:115-124`). It refuses a completeness figure, a coverage percentage, or any single number standing for the person. It also refuses to order itself: no `order`, `pinned` or `featured` field exists, and adding one would be a rank wearing an integer's clothes.

**BRANCH (a team).** `{id, name, branches[], leaves[]}` (`packages/enterprise-policy/src/bough.ts:54-59`) — teams nest, and a branch is the *only* level that should hold people. It may assert membership and structural counts: `limbSize` separates direct from total, because "conflating them is how a lead's team of four gets reported as forty" (`bough.ts:95-103`). **The refusal of a team figure is asserted in the domain and BROKEN in the shipping renderer:** `apps/enterprise/src/renderCompany.ts:136` computes `limb.leaves.filter((l) => isPublic(stateOf(store, l.id))).length` and `:147` prints it per limb as `Public: <n>`. Two teams' `Public` cells side by side in one org chart is a comparison between teams.

**BOUGH (an organization).** `{id, name, branches[], leaves[]}` (`bough.ts:67-72`). It may assert which teams hang off it. **It must refuse to hold people directly, and today it does not:** `bough.ts:30-32` argues for bough-level leaves, `apps/enterprise/src/companyDocument.ts:198-211` loads them, `renderCompany.ts:134-152` renders `limb.leaves` identically for bough and branch through `Limb = Bough | Branch` (`bough.ts:82`), and `pathToLeaf` can legally return a path ending at a bough (`bough.ts:162-177`). `bough.ts:34-38` says the no-aggregate refusal "has to hold hardest here" — and here is where it is broken.

**TREE (a company).** Two shapes, and the taxonomy is broken on **both** planes. `CompanyTree {id, company, boughs[]}` (`bough.ts:75-79`) has **no** `leaves` field, so on the enterprise plane a person cannot hang off the trunk by construction — that is the technique the bough needs. The cloud plane is worse, and it is the one that renders publicly: `Tree {id, organization, leaves: readonly Leaf[]}` (`packages/canopy/src/canopy.ts:24-29`) has no bough and no branch at all, and `apps/canopy/src/renderTree.ts:302` renders `tree.leaves.map(...)` — **every person on the served public tree page hangs directly off the trunk.** That is a NOT BUILT gap in the public domain model, not a stylistic difference. The refusal that does hold: `canopySize` returns `{trees, leaves}` cardinalities only, because "a single figure summarising an organization's people is a rating of those people" (`canopy.ts:36-50`), and the page states its own omission in served bytes (`renderTree.ts:104-110`, `:128-131`).

**CANOPY.** The public layer, and **it is the gate a person prepares at — not the tier permitted to make network calls.** Crossing licenses exactly one new call: a person's own artifact reaching the service they chose. A published leaf makes zero third-party calls; a visitor consented to nothing. It may assert what was explicitly published and when, from what digest — `publishedAt` and `source.documentDigest` are required (`packages/canopy/src/publishedDocument.ts:597-605`, `:331`) — and the published artifact has no `tier` field at all, refused by name because every published leaflet is verified by construction (`publishedDocument.ts:246`, `:252-260`).

> **MEASURED PRECONDITION — what `verified` proves in this tree, exactly.** It is **not bound to a declared signer here.** `LOG_FORMAT = "%H%x1f%ae%x1f%G?%x1f%s%x1e"` (`gitIntake.ts:69`) reads no `%GS`; `%GS` appears only inside a comment (`packages/leaf/src/intake.ts:137`) and is never parsed. Attribution is `identities.has(normalizeIdentity(commit.authorEmail))` — the self-declared `%ae` (`intake.ts:437`). `signatureFinding` returns `"verified"` for git codes `G` and `U` (`intake.ts:257`, `:293`), with SSH `U` correctly demoted to `unbound` (`:292`). So `verified` today means: **git accepted a signature on a commit whose author field names a declared identity.** It does not mean the signing key is the subject's. Any key git accepts, on a commit authored as the subject, crosses the publish gate. Every count in §2–§4 is a count of *unbound* signatures until `%GS` is read and required to match a declared identity. The caracas worktree already reads `%GS`; this tree does not, and landing that is prerequisite to everything above the leaflet.
>
> **This contradicts ENGINEERING-PLAN, and the plan is the side that is wrong for this tree.** Its §10 table row 1 (:320) reads "signer-binding shipped", and §6:203-208 describes `%GS` as the fix for a false `verified`. Re-measured this run: `%GS` appears in this tree only inside a comment (`intake.ts:137`) and `LOG_FORMAT` (`gitIntake.ts:69`) does not request it. What *did* ship is the narrower half — the SSH `U` → `unbound` demotion at `intake.ts:292`, which stops one specific false `verified` — and the plan's row overstates it into the general claim. The stakes are not documentary: `apps/canopy/src/renderPublished.ts`, the `pub-work` note (grep "Each of these had its authorship" — **no line number, deliberately**: this citation moved three times inside one PR, 237 to 247 to 265, and was written stale twice; a quoted string is the anchor that survives an edit to the file it points into) tells a public reader, in served bytes, that "Each of these had its authorship cryptographically established before it was published". The tie is to the self-declared `%ae`, not to the signer. That sentence is the overclaim, and it is on the one surface a stranger reads. *(2026-09-04: this pointed at `:215-217` and quoted "a signature that git checked and accepted, tied to a declared identity" — a SECOND sentence, in the empty-leaf branch, which F-030 deleted because it stated one withholding cause when the gate has three. The overclaim above it survives and is what this paragraph is about.)*

## 2. LEAF COMPOSITION, REFRESH, AND SUPERSESSION

**The time gap, and the cheapest honest fix.** No leaflet records when work happened. `LEAFLET_KEYS` is closed at five (`document.ts:68-74`), and the only instant on a leaflet is `provenance.observedAt` — one `new Date().toISOString()` per run (`apps/leaf/intake.mjs:312`) copied onto every leaflet of that run (`intake.ts:455-459`). **The two roots differ, and the correction is worth having:** the leaf git-intake root captures no date at all (`LOG_FORMAT`, `gitIntake.ts:69`), but the photosynthesis root already gathers one — `gather.ts:106` logs `--format=%H%x1f%s%x1f%aI%x1f%ae` and `authoredAt` survives to `drafted.summary` (`gather.ts:30`, `drafter.ts:91-92`) before being dropped at the seam, because `toLeaflet` carries only id, title, tier and provenance (`promote.ts:42-54`). So on one root this is a capture problem and on the other it is purely a seam problem.

ENGINEERING-PLAN §9.2:352-354 asks for "the period its evidence spans (a git cluster's first..last commit)". **A `{start, end}` period on the leaflet is more than the problem needs:** on the leaf-intake root one leaflet is one commit (`intake.ts:460`), so it degenerates to `start == end`. So put **the artifact instant on `Provenance`** — beside `ref` and `observedAt`, where "when the evidence was" already lives (`leaf.ts:50-58`; `PROVENANCE_KEYS` at `document.ts:75`). `LEAFLET_KEYS` stays closed, and this is independent of ENGINEERING-PLAN §12.1:475-478 (opening the leaflet body), which the sibling capture spec answers separately — the two changes do not depend on each other in either direction. **It is still an owner decision, and the first draft of this section was wrong to say otherwise:** `PROVENANCE_KEYS` is itself a closed set, so adding to it is a format migration of the same class as opening `LEAFLET_KEYS`, and LEAFLET-CAPTURE-SPEC §9.2 carries it as open decision 2. Two riders: the field is optional and absence is a labelled state, never a sort-to-bottom; and a git author date is self-declared (settable via `GIT_AUTHOR_DATE`), so a page may say *evidence dated March 2026* and may never say *worked on this in March 2026*.

**Order is document order, and the page says so.** Any stored order field is a rank in disguise — `packages/canopy/src/republish.ts:69-76` settled it for published artifacts ("the ordering of a published page is not a statement about the work"). **There is no default grouping by tier:** making `PROOF_TIERS` declaration order the primary key is a tier comparison performed in presentation, and `leaf.ts:30-48` refuses a comparator in either direction. The page renders in document order and prints that it is document order — the technique `renderTree.ts:128-131` already proves in served bytes. Grouping by tier, year or `provenance.source` is a **reader-supplied control**, never a default. Grouping by *theme* or *highlights* is refused: a theme is a claim about the shape of a career with no ref behind it (ENGINEERING-PLAN §8:254).

**Refresh is a re-runnable check beside the tier, never inside it.** Findings are `intact` / `changed` / `unresolvable` / `unchecked` (ENGINEERING-PLAN §9.1), riding beside the three-value tier. **Measured: none of it exists** — a repo-wide grep for `supersed|freshness|revalidat` over `packages/ apps/ scripts/` returns one unrelated CSS comment (`packages/foliage-tokens/src/tokens.css:54`).

**Two constraints the re-run must satisfy or it must not ship.** (a) **`unresolvable` from LOST ACCESS and `unresolvable` from CHANGED EVIDENCE are different facts and must never collapse into one value** — a departing person loses reach to internal refs, and the first post-departure run would otherwise mass-demote a leaf that nothing is wrong with. Neither may ever be re-rendered as doubt about the person. That is precisely ENGINEERING-PLAN §12.8:493-499, whose durable-digest answer "has to be designed at CAPTURE, not at departure" — so the re-run is blocked on §12.8 as well as on the provenance instant. (b) **A re-run must never silently discard or un-reject a human decision** (§9.2:356-358). The seam already behaves this way one layer down: `promoteApproved` appends only, skips ids already promoted, and marks `promotedAt` for idempotency (`promote.ts:6-7`). Supersession is that discipline applied one level up, not a new mechanism.

## 3. ORGANIZATIONAL SHARING AND THE PRIVATE COMPANY CANOPY

**The consent rule is settled** (ENGINEERING-PLAN §11b:415-419): internal visibility — branch → bough → tree — is consented by employment, with no per-leaf opt-in. **Employment consents to VISIBILITY; it does not authorise MEASUREMENT over the people at a scope.** Publication is a separate, explicit, typed-confirmation act. This workflow is not proof of human presence when a shell-enabled agent holds the same local authority.

**What exists today.** `ReleaseState` is six states, `internal` glossed "the only safe default" and `live` "actually reachable in the public Canopy" (`packages/enterprise-policy/src/release.ts:19-31`); `isPublic` is the single public question and exactly one state answers yes (`:128-136`); `applyEvent` distinguishes "not a legal transition" from "not permitted for this actor" and never returns a state on failure (`:142-149`). The store is keyed by a bare leaf id with `DEFAULT_STATE = "internal"` (`apps/enterprise/src/releaseStore.ts:34-37`, `:52-54`). There is **no scope model at all**: the actor comes from `FOLIAGE_ACTOR`, defaulting to `policy_owner` (`apps/enterprise/server.mjs:47-48`), and any GET renders the whole chart. Inside a company, today, everyone sees everything.

**Design: do not build a second permission system.** Reuse `applyEvent` verbatim and make the store key a pair — `` `${leafId}@${scope}` `` with `Scope = "branch" | "bough" | "tree" | "public"`. `${leaf}@public` **is** today's record with today's meaning, so existing stores migrate by suffixing the key, and `isPublic` is only ever asked of that record — enforced by splitting the accessor. Four invariants, each a defect if broken:

1. **An overlay may only narrow** what the level above permits; there is no widening control anywhere.
2. **Approval is not publication** — `approved` is a legal state `isPublic` answers `false` to (`release.ts:26-27`, `:134-136`), so a tree-scope approval must never imply a public transition.
3. **No count over the people at a scope, at any limb, ever.** Four rungs layered over `renderCompany.ts:136,147,224,267` would turn one cross-person aggregate into a four-column exposure ladder per team. Fixing those existing cells is part of this work, not a follow-up.
4. **`Scope` is rendered per-person as a containment label, never as a position on a scale.** Four ordered values plus a monotone narrowing relation *is* a comparator — the thing `ProofTier` deliberately refuses — so it must not escape the narrowing check and must never reach a rendered surface.

**A person leaving revokes the three internal scopes and touches neither the leaf nor any published artifact — as policy. As mechanism it is NOT BUILT.** `apps/enterprise/server.mjs` serves seven routes and not one of them is export, download or takeout — three static assets (`:158` `/tokens.css`, `:162` `/foliage.css`, `:166` `/fonts/`) and four pages and actions (`:181` `/`, `:192` `/releases`, `:203` `/members`, `:214` `POST /release`), with the 404 at `:240`. *(Citation re-read 2026-09-03: this sentence said "five routes only (`:126`, `:130`, `:134`, `:149`, `:160`; 404 at `:186`)", which was true on 2026-08-18 and had since drifted. The absence it reports had not changed — only the line numbers and the count had.)* The enterprise leaf is a file at a manifest-relative path on the **company's** disk (`companyDocument.ts:198-202`). "The leaf lives in the open plane so the subject keeps it" is a licensing fact about `@foliage/leaf`, not a mechanism by which a departing person obtains their document. **Where the mechanism will live is now marked** (owner, 2026-09-03; `PRODUCT-ARCHITECTURE-SPEC.md` §13.1): `apps/member` / `@foliage/member-app`, plane `enterprise` — the Individual-Enterprise surface, which owes takeout as its first route rather than its last. Still NOT BUILT; naming the address does not build it.

## 4. THE PUBLIC CANOPY: DISCOVERY WITHOUT RANKING

**What crosses, today, measured.** Only `verified` leaflets — pending and excluded are withheld entirely with the reason printed per record (`packages/canopy/src/publish.ts:76-84`, enforced `:484-511`). A declared example publishes nothing at all (`:86-93`). The gate ships its own limits with every review (`PUBLICATION_LIMITS`, `:243`). Publication takes `--confirm <id>` naming the leaf, and a second publication additionally needs `--republish`, because "a second publication is a second decision" (`apps/canopy/publish.mjs:21`, `:32-33`, `:474`). Ingest re-runs the gate and refuses any artifact it would have withheld (`publishedDocument.ts:101-108`).

**Discovery is a filter the reader supplies, never a set we select.** ENGINEERING-PLAN §11b:443-455 draws the line by *who forms the judgement*: a recruiter querying "verified Rust leaflets since March" is a filter over published facts — build it; Foliage computing "emerging talent" is an assessment of persons delivered to employers, and is a score whatever it is called. Ordering is by an artifact-borne instant **the reader chose**, never by count and never by tier. The sharp edge: a git author date is producer-settable (`GIT_AUTHOR_DATE`), so a self-hosted subject can move themselves up a recency sort — any offered sort key must be labelled as self-declared. There is no relevance weight, because a weight is a score. **NOT BUILT: no search, index, browse or listing code exists** — `/tree` and `/leaf/<id>` are the only dynamic routes (`apps/canopy/server.mjs:119`, `:158`); tracked as C12, GATED.

**"What changed between two publications of one leaf" — the SET, never the CARDINALITY.** The admissible form is a difference between two published artifacts of the same subject, rendered as **the enumerated added and removed leaflets, each with its instant and its ref** — the literal "here they are" of ENGINEERING-PLAN §11b:450-455. The reader counts if they wish; we never do. Hard exclusions:

- **No count of added, removed, changed or withheld is ever rendered as a standalone figure, emitted into a `data-*` attribute, or exposed as a queryable or sortable field.** A per-person scalar delta furnished to an employer is a ranking the moment there are two browser tabs. The single-subject test does not save it — every credit score is single-subject too. **This rule is not confined to the diff:** it governs every surface below it, and the cross-check caught it being broken one level down — the first draft of the sibling capture spec put `data-body-elements="N"` on the leaflet body's `<ul>`, which is the same integer with a different name. It is removed there (LEAFLET-CAPTURE-SPEC §5 item 4), and `elementsWithheld` is a boolean for the same reason (§6 there).
- **The name matters.** This is not called "emergence": R7 refuses an "emerging talent" set, and the word imports the semantics the feature must refuse.
- **`withheldBefore` / `withheldAfter` (`republish.ts:128-129`) must never cross to any public surface.** Published-vs-withheld is the completeness ratio R3 already refuses (`leaf.ts:115-124`), assembled by the reader from two integers. This is live today, not hypothetical: `publishedDocument.ts:906` writes `withheld: {count, kinds}` and `apps/canopy/src/renderPublished.ts:187` emits `data-withheld="${w.count}"` into served bytes — even though `renderPublished.ts:36-37` states in that same file that withheld is rendered "as entries and kinds — never as a number of leaflets".
- Decline-symmetric: the same layout must render "nothing added" and a removal set with equal prominence.

The machinery is half-built and pure: `diffPublications` is total and deliberately order-blind (`republish.ts:69-80`, `:125-129`), used once, pre-egress (`publish.mjs:474`). What it lacks is a **publication chain** — and the owner question there is not retention; see §7 C.

**The honest state of the public canopy today: it is empty.** STATUS C1/C2/C5 record 0 verified leaflets across thousands of real commits, because nothing on this machine is signed, and `renderPublished.ts` renders that plainly (grep "Nothing on this leaf could be published" — a quoted anchor rather than a line, for the reason given at §6b item 7) ("Nothing on this leaf could be published as a claim"). Everything in this section is being designed against a page that has never held one verified leaflet.

## 6. NOT BUILT — absent from the tree, measured

1. **An artifact instant on `Provenance`** — `PROVENANCE_KEYS` is `{source, ref, observedAt}` (`document.ts:75`); the leaf intake root's `LOG_FORMAT` carries no date (`gitIntake.ts:69`); `observedAt` is one run clock (`intake.mjs:312`). Not absent everywhere: the photosynthesis root gathers `%aI` (`gather.ts:106`, `:30`) and discards it at `toLeaflet` (`promote.ts:42-54`).
2. **Freshness / supersession / revalidation** — repo-wide grep finds one unrelated CSS comment (`tokens.css:54`).
