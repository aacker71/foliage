# Complete portfolio-scale product: acceptance matrix

Planning record, 2026-09-07. The target is the complete product at every portfolio level and across all five offers. Delivery may be sequenced; an unfinished level or offer remains required. This document records acceptance requirements, not completed implementation, customer success or production readiness.

The architecture is fixed for this plan: Vercel hosted apps, Clerk SSO, Supabase Postgres authority, private Supabase Storage for explicitly shared artifacts/media, Novu delivery, and personal source evidence kept local. D3–D9 and the approval interaction contract govern every row. Clerk is the selected hosted identity provider; Supabase remains storage and transactional authority. This engineering choice does not claim a configured deployment.

Sources: [scale decisions and approval contract](PORTFOLIO-SCALE-ENGINEERING-PLAN.md), [launch outcomes and T01–T20 scenarios](LAUNCH-TO-CUSTOMERS-PLAN.md), [five-offer specification](HISTORY-PRODUCT-ARCHITECTURE-SPEC.md#13-where-the-two-unbuilt-owner-apps-go--decided-2026-09-03-built-nowhere), [UI foundation](UI-FOUNDATION.md), and [current local release-storage limits](ENTERPRISE-RELEASE-STORAGE.md). Historical capability statements in source documents are not current acceptance evidence.

The [complete build plan](PORTFOLIO-SCALE-BUILD-PLAN.md) is the execution map for these requirements. The [agent ecology](AGENT-ECOLOGY.md) supplies the existing roles and enterprise private-deployment scope; neither a role name nor a deployment label establishes implemented behavior.

## How acceptance is recorded

- Every row starts **Required — evidence pending** in this matrix. Existing evidence can be linked after its exact scope and candidate are checked; a local test does not establish a hosted guarantee.
- Each evidence record names the row ID, accountable owner, commit, environment/deployment, date, exercised route/action, expected and observed outcome, failure/recovery result, and remaining defect. Use Required, Implemented, Awaiting validation, Accepted or Blocked with the precise missing dependency.
- Technical evidence uses actual test execution, database/object-store and process boundaries, deployment configuration, fault injection and browser observations. Identify synthetic test inputs as harness data. Customer evidence uses consenting participants and authorized source material; record interventions and observed difficulty without inventing timing or outcomes.
- Store credentials, raw evidence and participant details outside public reports. Attach redacted receipts, traces and observations sufficient to assess the result. Re-run affected evidence when implementation, policy, provider configuration or supported formats change.
- No aggregate completion percentage substitutes for a row's evidence. The complete-product claim requires every row and every applicable supported configuration; unresolved consent, offer or operating decisions remain named gates, not discarded scope.
