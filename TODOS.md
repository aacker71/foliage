### P3 — Additional source connectors beyond the first supported offer

**What:** Add source adapters beyond the source types required for the accepted first customer.
**Why:** Broaden usable evidence only after the current intake-to-reader workflow proves useful.
**Pros:** More customers can use their actual work; fewer manual operator conversions.
**Cons:** New permission, attribution, malformed-input, privacy and support surfaces for each adapter.
**Context:** Current implementation is strongest on git, with photo/brain paths carrying distinct prerequisites. L1 must support the chosen customer's real material; this item cannot defer a connector that the first offer already promises.
**Effort:** L; human ~1–2 weeks per substantive adapter / agent ~1–2 days plus real-source validation.
**Priority:** P3
**Depends on:** First-customer/source decision, observed demand and existing source/promotion contract.

### P3 — Hosted source playground

**What:** Consider an optional browser evaluation flow for permitted material.
**Why:** Reduce installation friction if actual observations show local setup prevents otherwise useful adoption.
**Pros:** Easier evaluation; clearer supported-source demonstration using the user's real material.
**Cons:** Adds upload/retention/consent obligations and hosting cost before value is established.
**Context:** No hosted source playground is in the initial implementation scope. The review chose the existing deterministic local CLI/browser first-result vehicle; do not seed a demo portfolio or silently upload private source material to make a playground attractive.
**Effort:** L; human ~1–2 weeks / agent ~1–2 days plus privacy/security acceptance.
**Priority:** P3
**Depends on:** Measured setup friction, supported source format, approved hosted admission/retention and owner scope decision.

### P3 — Broader public discovery and recruitment distribution

**What:** Extend opt-in discovery beyond directly shared portfolio URLs when its existing product gate opens.
**Why:** Let consenting subjects reach relevant readers without asking them to distribute every link manually.
**Pros:** More reader access and a clearer acquisition path for the recruiter track.
**Cons:** Enumeration, indexing, removal and membership relationships widen disclosure risk.
**Context:** Recruiter scope remains preserved in the launch plan; this expansion does not authorize ranking, scores, silent indexing or exposure of private sibling counts. Existing noindex and explicit-public rules stand until the owner chooses the discovery contract.
**Effort:** L; human ~1–2 weeks / agent ~1–2 days plus consent/reader validation.
**Priority:** P3
**Depends on:** Hosted withdrawal proven, approved discovery contract and the recruiter/first-buyer gate.

### P3 — Custom billing portal beyond the accepted paid offer

**What:** Build custom account/billing management only when the provider's supported flow fails a real accepted requirement.
**Why:** Handle future commercial complexity without making a bespoke portal a prerequisite for a simple paid pilot.
**Pros:** More control over complex organizations, invoices and plan management.
**Cons:** More payment state, reconciliation, support and security work to maintain.
**Context:** Payment, cancellation, receipt, entitlement and help for the first paid offer remain mandatory at L5. This item defers only custom/generalized portal features; billing never controls subject ownership or publication consent.
**Effort:** M/L; human ~1 week / agent ~1 day plus provider and customer acceptance.
**Priority:** P3
**Depends on:** Approved offer, actual provider limits and observed billing workflow needs.

### P3 — Advanced botanical exploration beyond the accepted native journey

**What:** Add richer exploration interactions after the readable collection/detail/return flow is accepted.
**Why:** Help readers navigate genuinely large portfolios when native sections or bounded pages are insufficient.
**Pros:** Purposeful botanical navigation and better orientation across large real collections.
**Cons:** Accessibility, state/history, motion and framework/CSP complexity; geometry can accidentally imply ranking.
**Context:** The required first UI slice still uses Foliage tokens, correct mark, readable actual work and native links/disclosures. Wider app adoption follows the UI foundation; this item does not defer required shadcn/Magic adoption or replace it with a separate design system. No hover-only evidence or generated portfolio may fill the explorer.
**Effort:** M/L; human ~1 week / agent ~1 day plus actual large-collection and owner visual acceptance.
**Priority:** P3
**Depends on:** Accepted first slice, actual scale/navigation friction and preserved no-score/accessibility contract.
